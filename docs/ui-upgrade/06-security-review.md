# 06 - Security review of the back-office upgrade

Reviewer: Security Reviewer (read-only audit). Date: 25 November 2026. Branch `ui-upgrade`, everything changed since `c7f15d1` under `admin/` (185 files, nine migrations `20261125000100` to `20261125001000`).
Method: read every migration, server action, page, API route and the pitch code; ran read-only SQL against the local database (role switches inside rolled-back transactions, nothing kept); `curl` without a session. No tests were run, no browser login, nothing changed.

## Summary

1. No Critical and no High finding. The database layer is well built: every new table has row-level security, `anon` has nothing, no function can be called by `anon`, there is no dynamic SQL anywhere, and every `security definer` function has a fixed `search_path` with `pg_temp` last.
2. The core promises hold: a Detected or rejected record cannot reach `creator_sponsorship_facts` or the Claude prompt; a person and a note are required to confirm; nothing is saved approved; nothing is sent without the Send route; an opt-out by a contact person still blocks that address, and a creator's opt-out works as before.
3. Four Medium findings. A worker can take a sponsor off Do not contact (a creator needs the owner). Two new export functions let any worker pull every email, phone and contact person in one call with no audit line (this widens the accepted risk H03). An approved email to a contact keeps the old address if the contact's address is edited. Public applicant text reaches the Claude prompt, and the draft checks do not catch a bare email address or domain.
4. Seven Low and several Info items, mostly small guard gaps and audit completeness.
5. Score: **8 / 10** (the old code scored 7). Held back by the Medium findings, which are small fixes, and by the accepted H03 risk which the new tables extend.

## Replaced functions: every behaviour difference

**`log_audit`** (old: `20261123000400`, new: `20261125000400`). Two differences. The allowed list gains `brand.viewed`, `brands.exported`, `brands.imported`, `sponsorships.imported`. The owner-only list gains `brands.exported`. Nothing else changed (same checks for 2FA lines, 8 KB limit, actor rule).

**`audit_row`** (old: `20261123000200`, new: `20261125000900`, which copies `20261125000400`). Differences: (1) the label of a sponsorship is the sponsor's name (or the raw name), the label of a contact person is the full name, never the email; (2) new entity details for `sponsorship` (creator id, brand id, label, origin), `brand_contact` (brand id) and `list` (kind); (3) email lines also carry `brand_id` and `recipient_kind` (ids only); (4) the four cached counter columns on creators and brands are skipped, so a counter-only change writes no line; (5) for `brand_contact` the email, phone, LinkedIn link and notes are stored as `{"changed": true}`; (6) a sponsorship update is named `confirmed`, `rejected` or `restored` when the label or the `rejected` flag moves. Not changed: values up to 120 characters are still written for other columns, so a sponsorship's short `notes`, `evidence_note` and `video_title` appear in the log (not contact data).

**`emails_guard`** (old: `20261123000400`, new: `20261125000900`). (1) Recipient check: for a creator email it is the same `emails_check_address`; for `brand_contact` it requires the contact's current address and that the contact belongs to the sponsor (tested). (2) A change of sponsor, contact or kind counts as a content change (approved goes back to draft) and re-runs the recipient check. (3) Entering a queue state is refused when the sponsor is Do not contact, or when the contact's current address is on the suppression list. (4) Creator Do not contact and address suppression apply to every kind, including an email to a contact. Tested: a direct insert as approved is refused ("new emails must start as draft"); wrong address, or a contact of another sponsor, is refused.

**`reserve_send`** (old: `20261121000800`, new: `20261125000900`). Adds `sponsor_do_not_contact`, `no_contact` (contact deleted), and a suppression check that covers the contact's current address as well as the stored address and the creator's. Test mode, daily limit and gap are unchanged. Gap: SR-03.

**`mark_sent`** (same pair). A real send to a contact stamps `brands.last_contacted_at` and leaves the creator alone; a creator email behaves as before (stamps the creator, moves New to Contacted). Test sends touch nothing.

**`deals_before`** (old: `20261121000300`, new: `20261125000300`). The commission is `coalesce(commission_cents(amount), 0)`, so an empty amount gives 0 instead of an error. Nothing else.

## Checked and fine

- **Row-level security and grants (live database).** All nine new tables and `niches` have RLS on; staff read and write, owner delete; the link tables and `list_items` also allow staff delete; `saved_views` shows own plus shared rows, and writes only own. `anon` has no privilege on any new table or view and no execute on any new function (tested with `set local role anon`: permission denied on `sponsorships`, `brand_contacts`, `creator_sponsorship_facts`, `brand_summaries`, `creator_summaries`, `niches`, `saved_views`, `creators_export`, `sponsors_export`, `global_search`, `log_audit`). `creator_sponsorship_facts`, `brand_summaries` and `creator_summaries` are `security_invoker`.
- **Functions.** All list, facet, match, bulk, search and export functions are `security invoker` (RLS applies). The only `security definer` additions are `sponsorship_refresh`, `sponsorships_rollup`, `deals_make_sponsorship`, `audit_row`, `log_audit`, `reserve_send`, `mark_sent`; each has a fixed `search_path` ending in `pg_temp`; the first three and the trigger functions are not executable by any API role (`reserve_send` and `mark_sent` only by `service_role`, as before; a worker gets permission denied). No `execute` of text, no `format()` on user text (the only `format` calls build grants and policies from fixed names).
- **Sort value `match:<uuid>`.** Matched by a strict regex and cast to uuid; anything else gives no sponsor and falls back to subscribers. Text arguments go through `like_pattern` (escapes `%`, `_`, `\`, cut to 100) or are compared as typed values. `p_status` is cast to the enum (a bad value is an error caught by the page). Limits are clamped (100 rows for creators, 1000 for sponsors, 200 ids in bulk).
- **JIT setting.** `set jit = off` is a per-function setting that only changes the planner; it opens nothing. Cached counters: see SR-06.
- **Sponsorship label rules (live tests).** Worker: detected to confirmed without a note is refused; rejected to confirmed in one step is refused; restore is staff only; a confirmed record cannot go back or be rejected; `origin = 'deal'` and `deal_id` cannot be written by a client; `confirmed_by` and the time come from the login. `creator_sponsorship_facts` returned 0 detected or rejected rows. Gaps: SR-05.
- **Pitch prompt content.** `pitch-facts.ts` and `pitch-prompt.ts` take named fields only: first name, channel name and link, niche, subscribers (or "hidden"), average views; sponsor name, industry, target niches and size, a count of other channels; up to three confirmed past sponsors (name and month) from the facts view. The view is the only source (selected columns: brand, name, date, not the video title). The creator row passed in contains the email, but `buildPitchFacts` copies named fields and drops it. No notes, `audience_countries`, `evidence_note`, brand notes, budget, price, phone, contact email or contact role. Detected names are used only to refuse a draft and for the on-screen "Left out" list. Free text is cleaned (angle brackets out, one line, 300 characters). Gaps in this area: SR-04.
- **A draft cannot be approved or sent by itself.** Insert as approved is refused by the database; `draftPitchAction` saves with the default `draft`; sending needs the Send route and `reserve_send`. Test mode and the daily limit are unchanged. `editAction` runs the general draft checks again before approving.
- **Server actions and pages.** Every action in `sponsors/actions.ts`, `sponsors/profile/tag-actions.ts`, `creators/actions.ts`, `creators/list-actions.ts`, `creators/profile/actions.ts`, `deals/actions.ts`, `components/matching/actions.ts`, `components/outreach/actions.ts`, `lib/sponsorships/actions.ts` and `emails/review/actions.ts` starts with `requireStaff()` (or `requireOwner()`), validates with zod or the shared parsers, and uses the user's own client. Delete of a sponsor, contact person, creator and sponsorship stays owner only (action and RLS; tested: a worker deleted 0 rows). Fields are whitelisted (`validateSponsor`, `validateContact`, `validateCreator`), so no mass assignment. Messages shown to the user are fixed sentences; database detail only goes to the server log (code only). Every page under `creators`, `sponsors`, `deals`, `emails` calls `requireStaff()` except `creators/[id]/page.tsx` (SR-10).
- **Lenient uuid pattern.** `z.guid()` and the hand-written regex accept only 8-4-4-4-12 hexadecimal characters and dashes. They are used in `.eq`, `.in` and RPC arguments, and in the one place a filter string is built (`.or(...)` in `nameFilter`, `searchFilter`, imports) the text is double-quoted and escaped; the channel duplicate check in `creators/actions.ts:38` only receives characters allowed by `NAME` (no comma, bracket or quote). Safe.
- **API routes.** `search`, `sponsors/export`, `sponsors/import`, `sponsors/sample`, `creators/export`, `creators/import`, `emails/[id]/send` all use `apiHandler`. Without a session every one answers 401 and every page redirects to login (`curl`). Sponsor and creator export are owner only; the audit line is written first and the export is refused if it cannot be written; both are `no-store`. Imports: 1 MB, 2,000 rows, header and column-count checks, preview and commit both re-validate, audit line written in `finally` with counts only (no names or emails), cross-site POST refused by the Origin check. Search: query 1 to 100 characters, results hold names and one line of context only, `no-store`.
- **CSV formula injection.** Export puts a quote in front of cells that start with `=`, `+`, `-`, `@`, tab or CR (phone numbers that start with `+` and contain only digits and separators are left alone, which cannot form a formula). Import strips those leading characters from every cell. Both are covered for sponsors and creators.
- **Data exposure.** List rows, pickers, facet functions, search and the match reasons carry no email, phone, note or contact person (`has_email` is a boolean; pickers return names and one hint). Client components that receive personal data are the ones that must: `ContactPeople` (after the profile view), the creator edit dialog (edit mode only). `OutreachHistory` shows subjects and status, not addresses. The two profile pages write `creator.viewed` and `brand.viewed` with the name only. Audit rows checked in the live log: new `brand_contact` lines hold the name and ids only; no new line holds an email, phone or note (the only addresses in the log are in 43 old seed rows).
- **Browser side.** No `dangerouslySetInnerHTML`, `innerHTML`, `eval` anywhere in the diff. External links (`website`, LinkedIn, channel link) use `target="_blank" rel="noopener noreferrer"`; the website and LinkedIn are checked for `https` (and the LinkedIn host) at save time and again at render; the channel link must start with `https://` (database check: YouTube host). Saved views are re-parsed on apply (`cleanQuery` / `viewQuery` / `parseFilters`), always navigate inside the same path with `router.replace`, so a hostile stored query cannot redirect. "Copy link" only copies the page's own address built from validated filters. Redirects use fixed paths or a regex-checked query. The command palette stores only names and our own links (SR-17).
- **Sponsor opt-out and creator opt-out.** See SR-13 (tested in a rolled-back transaction).
- **Seed and tests.** See SR-19.
