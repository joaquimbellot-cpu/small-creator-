# 03 Database audit (agent 3)

## 1. Scope and method

- Read all 11 migrations (1,691 lines), the seed, the SQL tests and the app code that talks to the database (`admin/lib/creators/query.ts`, `filters.ts`, the deals, emails, inbox, audit and sending pages, `lib/assistant/tools.ts`, `lib/email/send.ts`).
- Ran `bash admin/supabase/tests/run.sh` on the shared local stack: **201 SQL checks + 39 HTTP checks passed, 0 failed** (two runs). Note: each run leaves about 9 append-only audit lines in the shared database.
- Made a scratch copy of the local database (`audit_db3`), loaded 50,000 creators, 200,000 emails, 20,000 deals, 500,000 audit lines, and ran EXPLAIN (ANALYZE, BUFFERS) as the `authenticated` role with the owner's JWT claims (so RLS applied). Also built a second empty scratch database from the 11 migrations to test order and re-running. Both scratch databases are dropped. The shared database was only used read-only, apart from the test suite above.
- Probed row-level security as `anon`, as the worker and as the owner (SQL, rolled back) and the worker through the real gateway with the anon key (`/rest/v1`, fake data only).
- Production was not reachable, so everything about production is `unverified`. Evidence below comes from the local stack. The project map says 27 policies; the database has 39 (15 tables, 30 functions).

## 2. Done well

- RLS is on for all 15 tables, with deny-by-default: `anon` has no table, view or function privilege at all (probed: 7 of 7 denied). `creator_summaries` is `security_invoker`, so RLS applies (anon denied, staff allowed).
- Every one of the 30 public functions has `search_path` set, and none has EXECUTE for `PUBLIC` or `anon`. The send functions (`reserve_send`, `mark_sent`, `mark_failed`), `opt_out`, `login_allowed`, `record_login_attempt`, `bootstrap_owner` and the two form functions are service-role only.
- Policies wrap helper calls as `(select is_staff())`, so they are evaluated once per statement, not per row. The 2FA rule (aal2 needed when a verified factor exists) is enforced inside `is_staff()` and `is_owner()`.
- `emails_guard` is strong: clients can only draft, edit, approve, un-approve and retry. `sending / sent / failed / replied` are reachable only through the functions (probed: worker `approved -> sent` is refused). A real email to a do_not_contact creator or a suppressed address is refused at insert and update.
- `reserve_send` takes a global advisory lock plus the row lock, checks approval, do_not_contact, suppression, test mode, postal address, daily limit and spacing in one transaction. `commission_cents` is the single source and is forced by a trigger (client cannot set it). Single settings row is enforced by `check (id = 1)` (probed: a second row is refused).
- Money is `bigint` cents, with `check >= 0`. Emails are `citext` with unique keys. Text columns have length checks. Foreign keys are deliberate (`deals` restrict, ids `set null`).
- `audit_log` is append-only by privilege and by triggers (update, delete, truncate), including for service role (probed: truncate and update refused). Triggers skip updates that change only `updated_at`.
- Proposals and assistant tables: owner-only, own rows only, messages append-only, proposal life cycle guarded by a trigger, approve is claimed atomically (`pending -> approved` with a status filter).
- The seed is fake only (every address `@example.test`, phones `555`), deterministic, and matches `EXPECTED.md` and `expected.json` exactly (statuses 18/12/8/10/10/2, emails 16/12/3/4/2 plus 3 test, deals by stage, 10 brands, 3 templates, 2 suppressed, all `manual`).
- All 11 migrations apply cleanly in order on an empty database (tested), each in one transaction.

## 4. Not checked or limits

- Production database: not reachable, so grants, extensions, publications (`supabase_realtime`), Supabase sign-up setting, and whether the hosted `postgres` role has `BYPASSRLS` (the `emails_guard` and send functions rely on `current_user` being a bypass role inside SECURITY DEFINER functions) are `unverified`. All 11 migrations are reported applied there; I could only test them on a fresh local database (Postgres 16, no Supabase extensions beyond citext and pg_trgm).
- Timings are from a local Postgres 16 on one machine with synthetic, evenly distributed data; real ratios (for example share of `creator.viewed` in the audit log) will differ. Concurrency (two simultaneous sends) was read, not load-tested.
- Not done: the gateway/PostgREST row limit (`max-rows`) and statement timeouts on hosted Supabase; HTTP-level checks of app routes (security agent); backup and restore on the free plan; `pg_stat_statements` (not installed locally).
- The test suite (`tests/run.sh`) writes about 9 audit lines per run into the database it targets and cannot remove them (append-only); the audit count of the shared stack rose from 66 to 84 during my two runs.
- No code, configuration or tracked file was changed. Scratch databases `audit_db3` and `audit_db3m` were dropped; scratch files are only in the scratchpad folder.

Score: 7/10: the database design is careful and well tested (full RLS, hardened functions, guarded email state machine, 240 passing checks), but a worker can bypass the audited, owner-only handling of personal data through the REST API, do-not-contact can be lifted by a worker or lost by a delete, and a few queries and indexes will not scale.
