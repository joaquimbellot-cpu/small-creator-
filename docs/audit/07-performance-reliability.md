# 07 Performance and reliability audit (agent 7)

## 1. Scope and method

- Read the brief, the project map, section 3 of the database audit (its IDs DB-04, DB-05, DB-07, DB-10 are referenced, not repeated) and the page, API, send, login, drafting and assistant code that talks to Supabase, Claude and SMTP.
- Ran on the shared local stack (fake data only): Playwright (Chromium, 3 runs per page, logged in as the owner) on the built app at :3000, with about 5,000 extra `ZZ AUDIT` creators (5,060 rows in total during the tests; the rest of the stack unchanged). Measured page loads, request counts, bytes, JS size and the number of Supabase session checks (from the GoTrue log).
- Outage tests: stopped and restarted only `smallfold-postgrest` and `smallfold-gotrue`. Ran a private copy of the app on :3107 (Claude and SMTP pointed at refused or silent local ports, `DRAFT_MODE` changed for that copy only), killed that copy mid-send, and removed it afterwards. No real email was sent; no real Claude call was made.
- Production timings are estimates: Supabase round trips counted from the code, times 150 ms, as the leader asked. Nothing was measured in production.

## 2. Done well

- Lists are paged on the server: the creators, emails and inbox pages return 25 rows with an exact count. Creators with 5,060 rows, a deep page, a search matching 5,000 rows, a sort and a filter all took 29 to 44 ms to first byte.
- CSV export pages through 1,000 rows at a time and gave all 5,060 rows in 121 to 222 ms locally (582 KB).
- Page weight is modest: 144 to 148 KB of compressed JavaScript per back-office page; the website is 36 KB in 4 requests.
- Tested: a Claude refusal in compose ends clearly ("0 drafts saved. Not drafted: ...", 2.3 s) and leaves no half-made drafts; the Claude page shows "Claude could not be reached. Try again." and releases its thread lock (`locked_at` back to null).
- Tested: a mail server refusal in a send returns 409 with a plain message and ends with the email in `failed` (not stuck); nothing was delivered anywhere.
- Tested: after PostgREST or GoTrue is stopped and started again, the existing owner session works again without a new login (no data lost).
- Tested: the login limit works (the 6th attempt for one made-up address was refused, on a separate test IP).
- Static website pages make no database or session calls, so they keep working when the database is down.
- Claude calls in the assistant loop have a time budget (`deadlineMs`, 120 s per call, step limit of 12), and the thread lock is taken over after a dead request.
- Login errors when the rate-limit check itself fails show "Something went wrong. Please try again." (tested while PostgREST was down), not a false lockout.

## 4. Not checked or limits

- Production was not reachable. Not checked: Netlify function time limits and cold starts, the Ohio to Tokyo latency (the 150 ms per call is the leader's estimate, not measured), the production JWT signing type (PERF-06), Supabase max rows and statement timeouts, and log retention on both platforms.
- Load was one user at a time. Concurrency, two simultaneous sends and the daily-limit race were not tested.
- Import (PERF-08) and export timeout (PERF-09) are from code reading; they were not run at 50,000 rows.
- Claude was tested only as refused and as silent. Recovery after a real Claude outage and the real draft time were not tested.
- Offline: Google Fonts failed to load (2 requests per page), so the local full-load times include failed font requests.
- The overview TTFB (360 ms at 5,060 creators) matches DB-05 and was not measured again. Stuck `sending` rows (PERF-03) match DB-04; the repair was not tested.
- Test residue: about 5,000 `creator.created` and 5,000 `creator.deleted` audit lines from my test remain, plus a few `auth.login` and `creator.viewed` lines from my logins and visits. The audit log is append-only and I did not disable any trigger, so they stay. My `ZZ AUDIT` creators, emails, the assistant thread and the test lockout rows were deleted; creators are back to 60. The mail catcher was not used, so no test mail was sent. The stand-in servers and the copy on :3107 are stopped. Both containers are running again. `git status --short` is clean apart from this report.

Score: 6/10. Core pages are fast and paged, and Claude or mail refusals are handled clearly, but a database or login outage gives wrong messages and locks people out, and a hung Claude or mail server can leave work half-done until someone runs SQL.
