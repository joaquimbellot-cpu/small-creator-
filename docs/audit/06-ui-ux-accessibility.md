# 06 UI, UX and accessibility audit

## 1. Scope and method
- Used the running app (http://localhost:3000) with Playwright and chromium as owner and worker. Every back-office page (overview, creators and its pop-up, import, deals, emails log, compose, review, one email, templates list/new/edit, inbox, claude, all four settings pages) and the login, forgot-password, reset-password, 2fa and unsubscribe pages, at 375x812, 768x1024 and 1440x900, with full-page screenshots and horizontal-overflow measurements.
- Ran axe-core 4.x (installed in the scratch folder) on every page at phone and desktop; measured text and border contrast by calculation from the design tokens; compared the website (`/`, `/apply`) with the back office (computed fonts, colours, radii, screenshots).
- Keyboard checks: tab order and focus ring, skip link, the creator pop-up (focus in, Tab trap, Escape, focus return), select-driven forms. Request interception (slow, aborted, HTTP 500) for loading and error states. Odd URLs for not-found pages.
- Read the shell, `components/ui` and CSS files to confirm causes. Nothing was created or changed in the app; only this report was added to the repo.
- Environment limit: the sandbox cannot reach Google Fonts, so the screenshots use the fallback fonts (Georgia and Helvetica/Arial) instead of Newsreader and Instrument Sans.

## 2. Done well
- The back office clearly belongs to the website: same cream, ink and pen-blue tokens (copied from `src/css/tokens.css`), serif headings at light weight, small uppercase sans labels, 8px corners, black uppercase buttons, paper-coloured fields.
- axe-core found no contrast, label, button-name or image-alt violations on any page. The only reports are the three below.
- Measured contrast is good: muted text 6.0:1 on cream and 6.5:1 on paper; badges green 5.56, amber 5.16, red 6.59 on cream; blue accent 6.3; cream text on ink buttons 16.8; chart blue 6.8 on paper.
- Visible focus ring everywhere (2px blue, offset 3px) and a working "Skip to content" link as the first Tab stop. Tab order follows the visual order.
- The creator pop-up is correct: focus moves to Close, Tab stays inside, Escape closes, focus returns to the link that opened it, body scroll locks, and on phone it scrolls inside itself. Delete and Discard ask "Are you sure?" in a proper dialog.
- Not-found pages for bad ids keep the navigation; bad query values (`page=-5`, `sort=zzz`, `creator=not-uuid`) are handled without errors. Empty states are written in plain English ("Nothing waiting. Every message has been handled...").
- Pages have a single h1 and a descriptive title; touch targets are at least 40 to 44px; the weekly chart has a "Show the figures as a table" alternative.

## 4. Not checked or limits
- Real Google fonts could not load in the sandbox, so exact font rendering and the heading size on the real fonts are unverified (fallback fonts were used; colours, spacing and layout were checked).
- Did not test wrong-password errors or the Claude chat (other agents cover them), email sending, or the 2FA code step (no authenticator; `/login/2fa` redirects to `/login` without a pending session).
- Screen readers (NVDA/VoiceOver) were not run; accessibility was judged with axe-core and keyboard tests. axe cannot judge wording or reading order.
- Worker role was only checked for login and the overview; the layout is the same shell, so layout results apply.
- Phone tests were in desktop chromium at 375px (no touch emulation or real device). The 500 error was simulated by intercepting the browser request, not by a real server failure.
- Other agents' "ZZ AUDIT" test records (including a 120 character name) were present while I tested; I did not create or change any data, so nothing needed cleaning up.

Score: 7/10 The back office matches the website well and passes automated accessibility checks, but it has no designed error or loading screens, a sideways scroll bug on phone tables, and a dropdown that saves on every key press.
